================================================================================
DSH Desktop 公告配置参数说明（notifications.json）
================================================================================

对应客户端版本：1.0.17
文档用途：说明公告配置文件里每一个参数的含义、可选值、以及每个值代表什么


--------------------------------------------------------------------------------
一、这个文件是什么
--------------------------------------------------------------------------------

客户端从与安装包同一个分发源拉取公告，完整地址：

    https://download.dsh.392700.xyz/notifications.json

放在这里而不是 GitHub Releases 的原因：与版本清单 latest.yml 同源，发布链路
已经跑通（上传顺序、校验脚本都是现成的）。由此带来一个关键性质：

    改公告内容不需要发新版本，也不需要用户更新应用。

想发一条维护通知，改这个文件、覆盖上传即可。已经装了的旧版本客户端会在
下一次启动或下一次 6 小时轮询时自动看到。


--------------------------------------------------------------------------------
二、整体结构
--------------------------------------------------------------------------------

文件最外层是一个对象，只有两个字段：

    {
      "version": 1,
      "notices": [ 单条公告, 单条公告, ... ]
    }


--------------------------------------------------------------------------------
三、顶层参数
--------------------------------------------------------------------------------

【version】
  含义      配置文件格式的版本号。
  是否必填  否。
  可选值    任意整数，通常填 1。
  说明      ★ 当前客户端**不校验这个字段**，它被完整忽略。写错、甚至整个删掉
            都不影响公告生效。保留它只是为了将来格式要演进时有地方放版本号。
            不要因为它写错而去排查公告为什么不显示。

【notices】
  含义      公告数组。所有公告都写在这个数组里。
  是否必填  是。缺这个字段整份文件作废。
  类型      数组
  条数上限  20 条。超过 20 条 -> 整份文件作废，客户端一条都不展示。


--------------------------------------------------------------------------------
四、单条公告的参数
--------------------------------------------------------------------------------

一条公告就是一个对象，字段如下。

--------------------------------------------------------------------------------
4.1 【id】  字符串
--------------------------------------------------------------------------------

  含义      这条公告的唯一标识。
  是否必填  是。
  格式      只允许英文字母、数字、点、下划线、短横线，长度 1–64。
            正则： ^[A-Za-z0-9._-]{1,64}$
  可选值    任意符合上述格式的字符串。
  代表什么  它是「已读记录」的唯一键。客户端用它在本地记下"这条你看过了"，
            下次就不再显示。

  ★ 三个必须知道的点：
    (1) 改了 id 就等于发了一条新公告 —— 所有人都会重新看到，包括已经读过的
        那些用户。id 一旦定下就别改。
    (2) 想让一条公告"下线"，正确做法是从 notices 数组里删掉它，或让它过期，
        而不是改 id。
    (3) 这个字段不参与任何文件路径拼接，但客户端仍按上述字符集收窄，避免
        将来有代码误用它拼路径。

  建议写法：带日期前缀，便于排序与排查，例如
      2026-09-30-maint-1004
      2026-09-30-client-1-0-17

--------------------------------------------------------------------------------
4.2 【type】  字符串
--------------------------------------------------------------------------------

  含义      这条公告以什么形态展示。
  是否必填  否。缺省为 "banner"。
  可选值与含义：

    "banner"  横幅。贴在 DSH 会话页面顶部，最多同时堆叠 3 条。**不打断**用户
              手头的工作，随时可以用右侧的 × 关掉。适合日常通知、版本说明、
              轻度提醒。

    "modal"   弹窗。走客户端自绘的对话框层（与「检查更新」「退出确认」同一
              套玻璃卡片），**延迟 10 秒**在 DSH 页面就绪后弹出。适合真正需要
              看到的重要事件：停服、强制升级、账号异常。
              它会进入对话框队列，因此不会和更新确认框叠在一起出现。

  注意      "modal" 没有条数上限（只有 "banner" 截断到 3 条）。如果配了 10 条
            模态公告，用户会连续被弹 10 次。请谨慎使用，模态公告一次最多
            放一两条。

--------------------------------------------------------------------------------
4.3 【level】  字符串
--------------------------------------------------------------------------------

  含义      语义级别，决定配色、图标，以及多条公告同时存在时的排序。
  是否必填  否。缺省为 "info"。
  可选值与含义：

    "info"      蓝色。普通信息：版本发布、使用提示、日常说明。
    "warning"   琥珀色（橙色）。需要注意但不紧急：即将维护、功能将变更。
    "error"     红色。必须马上知道：服务不可用、必须升级、Key 失效。

  配色      横幅左侧色条 + 图标颜色都由此决定。模态公告会复用对话框层
            对应级别的图标。

  排序      多条公告同时有效时，按 error → warning → info 排。最紧急的永远
            排最上面，不会被一条 info 挤下去。

--------------------------------------------------------------------------------
4.4 【title】  字符串
--------------------------------------------------------------------------------

  含义      公告标题，显示在第一行。
  是否必填  是。
  长度上限  60 个字符。
  格式      纯文本。换行符无效（标题只占一行）。
  注意      标题里的 HTML 标签不会被解析，会原样显示成文字。

  例：今晚 02:00–04:00 服务维护

--------------------------------------------------------------------------------
4.5 【body】  字符串
--------------------------------------------------------------------------------

  含义      公告正文，第二行起。
  是否必填  是。
  长度上限  2000 个字符。
  格式      ★ 纯文本。换行符 \n 会被保留并按原样换行显示。
  注意      ★ HTML 不会被解析。想加粗、用列表、插链接都做不到，只能靠换行
            和符号（例如用「- 」开头做视觉上的列表项）。

  例：
      维护期间 DSH 服务会短暂不可用，正在进行的会话会中断。
      其余功能不受影响。

--------------------------------------------------------------------------------
4.6 【link】  对象
--------------------------------------------------------------------------------

  含义      给这条公告挂一个"查看详情"的跳转按钮。
  是否必填  否。省略就没有这个按钮。
  子字段    label（按钮文字）与 url（跳转地址），两者都必须给。
  例：
      "link": { "label": "查看详情", "url": "https://example.com/status" }

  4.6.1 【link.label】  字符串
      含义      按钮上显示的文字。
      是否必填  是。
      长度上限  24 个字符。
      例        查看详情 / 查看更新日志

  4.6.2 【link.url】  字符串
      含义      点击后用系统默认浏览器打开的地址。
      是否必填  是。
      长度上限  2048 个字符。
      允许的协议  ★ 只允许 https:// 开头。
      被拒绝的  javascript: 、 data: 、 http:// 、本地文件路径 —— 全部会在
                解析阶段直接拒绝，并且**导致整份文件作废**（不是只丢这一条）。

      为什么不放开 http：公告内容来自可被篡改的远端文件，放开 javascript:
      等价于把 XSS 入口装进客户端。已读记录与安全约束见第六节。

--------------------------------------------------------------------------------
4.7 【startsAt】  字符串（ISO 8601 时间）
--------------------------------------------------------------------------------

  含义      这条公告最早什么时候开始生效。
  是否必填  否。省略 = 客户端拿到就展示。
  格式      ISO 8601，推荐带时区，例如 2026-09-30T00:00:00Z
            也可以写 2026-09-30T08:00:00+08:00。
  作用      定时发布。写一个未来的时间，到点之前用户看不到这条公告。
  注意      时间格式非法（例如写成"下周一"）会导致整份文件作废。

  例：
      "startsAt": "2026-10-01T00:00:00Z"

--------------------------------------------------------------------------------
4.8 【expiresAt】  字符串（ISO 8601 时间）
--------------------------------------------------------------------------------

  含义      这条公告什么时候自动失效、不再展示。
  是否必填  否。省略 = 永不过期。
  格式      同 startsAt。
  作用      自动下线。到点后客户端即使拉到这条也不展示，用户本地也不会
            残留横幅（下次拉取时消失）。
  约束      ★ 必须晚于 startsAt（如果两个都写了）。否则整份文件作废。
  ★ 强烈建议写。
            不写的话，一条忘记下线的公告会一直挂在所有用户页面上，直至用户
            手动 × 掉它。公告的寿命应该由你通过这个字段控制。

  例：
      "expiresAt": "2026-10-01T06:00:00Z"

--------------------------------------------------------------------------------
4.9 【dismissible】  布尔值
--------------------------------------------------------------------------------

  含义      横幅能不能被用户手动关掉。
  是否必填  否。缺省为 true。
  可选值与含义：

    true     可以关。显示一个 × ，用户点掉后这条记为已读，不再出现。
              绝大多数公告都该用这个。

    false    关不掉。没有 × ，横幅会一直挂在页面顶部，直到 expiresAt 到期。
              它也不会被记入已读，所以下次启动会再次出现 —— 这是"强制"
              语义的实现方式。

  适用场景    false：强制升级提示（不升级就用不了）、长时间停服公告。
              true：普通通知、维护提醒、版本说明。

  注意      这个字段只对 "banner" 有意义。"modal" 型公告本来就是通过
            「我知道了」或 Esc 关掉的。


--------------------------------------------------------------------------------
五、硬限制一览
--------------------------------------------------------------------------------

  项目                          上限      超出时
  ----------------------------  --------  ----------------------------------
  notices 数组条数              20 条     整份文件作废，一条都不展示
  整个文件大小                  256 KB    整份文件作废
  同时展示的横幅                3 条      多余的丢弃（按 error→warning→info
                                         排序后取前 3）
  同时弹出的模态                无上限    ★ 会连续弹，所以请少量使用
  本地已读记录条数              200 条    按标记时间升序，自动淘汰最早的
  网络请求超时                  8 秒      视为失败

  文件不存在（HTTP 404）        ——       视为"没有公告"，不是错误。
                                       这让客户端可以先于本文件上线。


--------------------------------------------------------------------------------
六、校验规则
--------------------------------------------------------------------------------

客户端在展示之前会**逐条**校验。关键点：

  ★ 任一条公告的任一字段不合法 -> 整份文件作废，一条都不展示。

这是刻意的设计，不是缺陷。半截公告（比如标题显示了、正文是空的，或者链接
按钮指向恶意地址）比完全没有公告更糟。

以下情况会导致整份文件作废：

  1.  文件不是合法的 JSON
  2.  最外层不是一个对象（比如写成了数组）
  3.  缺少 notices 数组，或 notices 不是数组
  4.  文件超过 256 KB
  5.  公告条数超过 20
  6.  id 缺失、不合规字符、或超过 64 字符
  7.  两条公告用了同一个 id
  8.  type 不在 banner / modal 之中
  9.  level 不在 info / warning / error 之中
  10. title 缺失、为空、或超过 60 字符
  11. body 缺失、为空、或超过 2000 字符
  12. link 不是对象，或 link.label / link.url 缺失、超长
  13. link.url 不是 https: 开头（javascript: / data: / http: 一律拒绝）
  14. startsAt / expiresAt 不是合法的 ISO 时间字符串
  15. expiresAt 早于或等于 startsAt
  16. dismissible 不是布尔值

这些规则不是纸面约定：项目里有一条命令
    node scripts/preview-notice.js
在**生成预览页时就会跑 12 类非法输入的断言**，任一条该被拒的没被拒，命令
直接失败中止。改了校验规则会立刻暴露。

另外三层安全约束（同样有断言守着）：

  - 正文与标题只用 textContent 渲染，永不解析 HTML
  - 注入脚本里唯一一处 innerHTML 是图标路径，那是主程序里的常量，不是远端
    传来的内容
  - 横幅的"查看详情"按钮走的是客户端既有的外链通道（带调用来源校验与
    协议白名单），不是新开一个浏览器调用


--------------------------------------------------------------------------------
七、已读行为
--------------------------------------------------------------------------------

  已读记录文件位置
      开发环境：  %APPDATA%\dsh-web-desktop\notice-read.json
      打包安装后：%APPDATA%\DSH Desktop\notice-read.json
      （两种路径不同是因为应用名在打包后才变成 "DSH Desktop"）

  文件内容形状
      { "read": { "2026-09-30-maint-1004": "2026-09-30T11:20:33.000Z", ... } }

  什么时候记已读
      - 横幅：用户点右侧的 ×
      - 模态：用户点「我知道了」，或按 Esc，或点遮罩
      （dismissible 为 false 的横幅关不掉，因此也不会记已读，每次启动都会
        重新出现，直到它过期）

  记了之后
      同一条 id 的公告不再展示。新的公告（有新 id）照常展示。

  排查用
      删掉这个文件 = 所有公告重新出现一遍，方便验证"是不是已读逻辑挡住了"。

  上限
      200 条。超出后按标记时间从早到晚淘汰。


--------------------------------------------------------------------------------
八、拉取时机与失败处理
--------------------------------------------------------------------------------

  什么时候拉
      1. 每次启动，DSH 页面就绪之后（不阻塞启动流程）
      2. 每 6 小时轮询一次
      3. 用户点击标题栏的铃铛（立即拉取）

  什么时候不拉
      开发环境（npm run dev）下，第 1、2 项自动拉取被跳过，避免打扰调试。
      但点铃铛的手动拉取在任何环境都会执行 —— 这就是开发期验证公告 UI 的
      办法。

  失败时
      启动与轮询路径：**完全静默**，只记一行日志，不给用户任何弹窗。
                  理由：断网是常态，如果每次开应用都弹"拉取失败"会很烦。
      点铃铛的手动路径：弹一个错误框说明原因。

  日志位置
      主进程控制台，形如
          [DSH] 拉取公告失败（startup）: 通知清单缺少 notices 数组
      排查配置问题时看这一行。

--------------------------------------------------------------------------------
十、发布与下线操作
--------------------------------------------------------------------------------

  上线一条公告
      1. 编辑 notifications.json
      2. 先本地验一遍：node scripts/preview-notice.js
         （它会跑全部校验断言，不过就失败，不会生成坏文件）
      3. 覆盖上传到
         https://download.dsh.392700.xyz/notifications.json
      4. 注意 CDN 缓存。如果传完客户端没立刻看到，在文件名后加时间戳绕过，
         或等待缓存过期。

  下线一条公告
      方式一（推荐）：从 notices 数组里删掉它。
      方式二：把 expiresAt 改成一个已经过去的时间。
      不要用改 id 的办法 —— 那等于给所有人发了一条新公告。

  没有版本号语义
      这个文件不参与版本比较，可以随时覆盖上传，不需要重新打包、不需要
      用户更新。它与安装包、latest.yml 只是共用同一个分发源。


--------------------------------------------------------------------------------
十一、常见问题对照
--------------------------------------------------------------------------------

  公告完全不显示
      → 多半是整份文件作废了。看主进程日志里有没有
        "[DSH] 拉取公告失败" 这一行，里面写了具体原因。
      → 确认文件真的传上去了（访问那个地址看得到内容）。
      → 确认 level / type 的值没有拼错。
      → 确认 expiresAt 还没到（过了时间会自动不显示）。

  部分公告显示，部分不显示
      → 不会这样。要么全显示要么全不显示（整份丢弃是全有全无的）。
        唯一"部分"的情况是：超过 3 条的横幅会有多余的被丢弃，
        模态公告超过 1 条会连续弹多次。

  改了内容但客户端没变
      → 缓存。等一会儿，或给文件名加时间戳。

  公告一直不消失
      → 很可能忘了写 expiresAt。补上并覆盖上传。

  想让用户重新看一遍某条公告
      → 删掉本地的 notice-read.json，或给这条换一个 id（后者会给所有用户
        都重发一遍）。
